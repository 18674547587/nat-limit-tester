# nat-limit-tester — 家用网络最大连接数压测

> 目标场景：老旧路由器（AR9331 级、16 MB 内存）在连接数上来后 CPU 打满、管理页失联、全屋断网。
> 本工具用来找出**「还能舒服用」的临界点**，而不是把设备压到死。

## 一、为什么不用现成的浏览器版

工作区已有的 `conn-stress`（<https://conn.260040.xyz>）是浏览器版，受三个限制：

| 限制 | 后果 |
|---|---|
| 单标签页先撑不住（几百到一千多） | 测不到更高 |
| 只能测「建连失败」 | 测不出延迟劣化，而「卡死」首先表现为延迟崩 |
| 无 ICMP / 无本地能力 | 无法区分是 WiFi、路由器还是光猫先崩 |

本项目的增量价值就在后两点：**延迟劣化判定** + **差分定位哪台设备先撑不住**。

## 二、架构

```
手机 App（造连接 + 探针 + 本地落盘）
   │  N 条 TCP 长连接，每条 = 1 条 NAT 会话
   ▼
家用路由器（被测对象）→ 光猫 → 运营商
   │
   ▼
服务端 hold_server.py（只 hold 不读写，独立计数）
   └─ HTTP /stats  /reset   ← 与 App 对账
```

服务端独立计数的原因：TCP 握手可能被本地 NAT 代答成功，客户端以为连上了，服务端其实没收到。**只有服务端自己数一遍才能对账。**

## 三、服务端

```bash
# 启动（默认 TCP 9001 保持端口，9002 控制面）
NLT_TOKEN=你的token python3 server/hold_server.py --max-conns 12000
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `--hold-port` | 9001 | 客户端连这里 |
| `--http-port` | 9002 | `/stats` `/reset` `/ping`，需 token |
| `--max-conns` | 15000 | 超过即拒绝并计入 `refused` |

实测（本机 894 MB 内存的 VPS）：12000 条连接时服务端 RSS 约 90 MB，可用内存仍剩 295 MB。
**建议 `--max-conns` 不超过 12000**，给同机其他服务留余量。

## 四、App

1. 填服务端 IP、端口、token
2. 路由器 IP 默认自动填默认网关；光猫 IP 手动填（可选，但强烈建议填——不然无法区分是路由器还是光猫先崩）
3. 开始测试

### 阶梯与判定

- 起始 50，步进 1.15×，硬顶 1200，每级保持 15 秒
- 每级并发建连窗口 200
- **判定顺序**：本机 fd 用尽 → 建连失败 → 路由器无响应 → 延迟劣化（超基线 5 倍）
- 任一触发立即全断，记录当前档位为临界值

### 三个数字要分清

| 数字 | 含义 |
|---|---|
| 本机 fd 上限 | App 进程文件描述符上限，超出就是 `EMFILE`，**不是路由器的问题** |
| 路径上限 | 路由器 NAT + 运营商共同决定，这才是你要的 |
| 服务端上限 | `--max-conns`，设太小会误判 |

## 五、已知限制

1. **WiFi 噪声**：手机连 WiFi 测试时，无线本身会先劣化。差分探测（路由器 vs 光猫）能部分分离，但要更准得用有线设备。
2. **fd 上限**：未 root 的 App 只能把 soft limit 提到 hard limit。多数机型 hard 是 32768，但部分 ROM 只有 1024，此时 App 最多建约 1000 条，会在结论里明确写「本机 fd 用尽」。
3. **UDP 会话数**暂未实现（第二版）。
4. 测完请等 2 分钟让 NAT 表项老化再测，否则结果偏低。
